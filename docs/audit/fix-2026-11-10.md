### Scope rule (owner decision to confirm)
- `supplier`: every booking item of the reservation must belong to a supplier the user has a `SupplierMembership` for.
- `agency_partner`: same check, where the supplier set is the user's own `SupplierMembership` rows plus `Agency.supplier_id` of each agency the user is an explicit `AgencyMembership` member of. This is the same relation the Safarsaz partner scope already uses. An agency with no linked supplier is denied. **Selling a booking on an agency's sales channel does not grant fulfilment.**
- `platform_admin` (`platform:manage`): tenant-wide override kept as before. Each use now writes an `AuditEvent` (`reservation.fulfill.admin_override` / `reservation.voucher_reissue.admin_override`).
- Any other role that may later get `reservation:fulfill` is denied until a scope rule is written for it (fail closed). `tenant_admin` and back-office roles never had this permission, so their behaviour is unchanged.
- Multi-item reservations: all items must be in scope (stricter than before, where only the first item was checked).
- **Owner decision (review N2):** a package whose items come from different suppliers can currently be issued only by a platform admin. The supplier ready-queue still lists it to each supplier, who then gets 403. Options: keep this rule and filter the queue, or add per-item fulfilment. Not changed on this branch.
- Admission tickets (`/admission-tickets/validate`, `/admission-tickets/redeem`) use the same rule. The venue's supplier must be in the caller's fulfiller scope, the platform admin override is audited, and every other role is denied (review N3).
- Platform admin overrides are recorded as an attempt in their own committed transaction, before the action runs. The record survives a refusal, an idempotent replay or a rollback. If it cannot be written, the override is refused (review N1).

### Customer price-breakdown fields
`view, currency, id, booking_id, total_selling_price, service_fee, discount_amount, discount_source, promo_code, vat, airport_tax, i6_tax, red_crescent, other_taxes, calculated_at`.
`currency` comes from the reservation's price snapshot. No frontend code calls this endpoint (checked with `git grep`), so no UI change was needed.

The internal settlement path (`reservation_funding` capture/release) relied on replay returning an entry of a different type. It now catches `LedgerCommandConflict` and skips silently, which keeps the previous outcome.
